# Luca ticket workspaces

## Defaults (override from the request or edit here)

- Root: `~/Luca` (multiple independent Git repos, not one repo).
- Canonical Herdr hub: one long-lived Luca hub Pi at `~/Luca`, normally labelled `Luca · tickets`, with explicit Git provenance anchored on the main `luca-backend` checkout. Reuse the established hub; do not create a new one per ticket.
- Worktrees: `~/Luca/.ticket-worktrees/<ticket>/<repo>` (`<repo>` is the checkout directory, e.g. `luca-backend` or `luca-ims`). Resume older checkouts where they are; do not move or duplicate them.
- Herdr workspace label: `Luca · <ticket>`; one worktree workspace and one Pi owner per code ticket, even when it touches multiple repos. New single-repo Pi sessions start at that checkout; new multi-repo coordinators start at the common ticket directory. No per-repo shell tabs by default.
- Base: each repo's `origin/main`, unless the task calls for another branch. Fetch when useful; never switch or reset the primary checkout to make room.
- Intent: shipping work → reviewable PR(s) in the changed repos; investigation → findings; exploration → ongoing session if useful, no automatic PR. Do not merge or deploy just because a PR is ready.

Use a ticket ID safe as one path component (not `.` or `..`; for example `LHD-123`), check for path collisions, and validate branch names with `git check-ref-format --branch`; choose repos and branch names from the task. Shell `~` only expands unquoted; use `$HOME/Luca` when quoting a path. Read the generic Herdr skill for control rules and the touched repos' `AGENTS.md` for code conventions.

## Session role and Pi defaults

- Default to an independent, persistent ticket session the user can work with directly—not a temporary worker reporting to the hub. Opening/starting a ticket, even with a task to forward, is a handoff rather than a request for supervision.
- The hub's default job ends after setup, startup verification, optional task submission, and reporting where the session is. Do not wait for findings, monitor progress, inspect/review changes, rerun checks, or send supervisory follow-ups unless explicitly requested. Monitoring/supervision does not itself request independent review or verification. Use this handoff flow instead of the generic Herdr background-worker wait recipe.
- Fresh hub and ticket Pi sessions default to `xhigh`. Use the user's requested provider/model, otherwise the launching Pi's `PI_PROVIDER`/`PI_MODEL` (or saved Pi defaults if unavailable). Launch explicitly with `herdr agent start <unique-name> --kind pi --pane <pane-id> -- --provider <provider> --model <model> --thinking xhigh`. Never silently choose a cheaper model/lower thinking because this is another session. Explicit user preferences override these defaults; if a selected model cannot support xhigh, report the supported level actually applied.
- Resuming keeps that session's provider/model/thinking unless asked to change them; omit fresh-session flags on recovery. Verify identity/cwd/readiness via Herdr and model/thinking from Pi's startup display or native session metadata before forwarding a task; `agent get` alone does not expose thinking. Report the actual launch settings. Inspect only startup/identity/error evidence, not ticket findings, for this check.
- The ticket owner—not the hub by default—completes the requested scope, validates its own work, and produces reviewable PR(s) when asked to ship. No artificial first-slice limits or blanket bans on commits, PRs, or delegation.

## Start or resume

1. Check `HERDR_ENV=1` and read the installed Herdr CLI. A question alone isn't a request to create a workspace. For an actual start, infer ticket, repos and intent; ask only when a missing choice changes the work. Inspect worktrees and branch refs in every affected repo, plus all live Herdr workspaces/agents and candidate panes. Match the ticket's actual repo identities, checkout paths, branches, and owner—not just its label. Resolve the reuse/recovery cases below before creating anything; preserve other tickets and dirty primary checkouts.
2. Find the established Luca hub and reuse its hub Pi. If competing hubs are plausible, ask which is canonical; do not repurpose or close an older Luca workspace. If no hub exists, open the backend main checkout with `herdr worktree open --cwd <backend-main> --path <backend-main> --no-focus` and take the returned workspace/pane IDs. This records explicit Git provenance. Inspect `already_open` and existing agents before changing anything; open can reuse an older workspace. Label only a newly created hub `Luca · tickets`; do not pass `--label` on open and accidentally rename an existing workspace. If the returned workspace's ownership is unclear, ask. In an available hub shell pane, change to `~/Luca`, verify the shell's actual cwd, and start or recover its hub Pi using the launch/recovery defaults above.
3. Reuse an existing ticket workspace/owner, including older standalone or root-tab layouts. For a new code ticket, choose one affected repo as the anchor (backend when affected). When the hub's recorded repo matches the anchor, create/open through `--workspace <hub-id>`: `herdr worktree create --workspace <hub-id> --branch <ticket-branch> --base <base> --path <ticket-dir>/<repo> --label "Luca · <ticket>" --no-focus`. If the checkout already exists but has no workspace/owner, use `herdr worktree open --workspace <hub-id> --path <existing-checkout> --no-focus`. If the anchor is another repo, use `--cwd <that-repo-main>` instead; never accidentally create an IMS branch in backend or add an untouched backend checkout solely for nesting. Read IDs from the response. For an existing local branch without a checkout, omit `--base` so Herdr preserves its tip; a remote-only feature branch uses its remote feature ref as `--base`, not `origin/main`.
4. For each other affected repo, reuse its existing checkout or add only the missing one: `git -C <repo-main> worktree add -b <ticket-branch> <ticket-dir>/<repo> <base>` for a new local branch, or `git -C <repo-main> worktree add <unused-path> <existing-local-branch>` for an existing one. Preserve remote-only feature tips when creating their local branch. **Don't use `herdr worktree create` again**: it would make another ticket workspace. Do not create a shell tab per repo. One owner coordinates the API and PR dependencies; extra panes/tabs are for a requested shell or an actual service/test need.
5. For a requested isolated research-only ticket workspace, create the unused common ticket directory and use `herdr workspace create --cwd <ticket-dir> --label "Luca · <ticket>" --no-focus`, without Git checkouts or environment provisioning. Otherwise research can stay in the current workspace.
6. Reuse the live ticket Pi or recover its known stopped session. Start fresh only when no resumable owner/session is known, or the user explicitly requests one. For a fresh session, use the returned or existing available shell pane, not another default tab. Keep the shell cwd at the checkout for a single-repo ticket; for a multi-repo ticket, use `herdr pane run <pane-id> "cd <shell-quoted-absolute-ticket-dir>"`. Use the same approach for a new hub Pi's `~/Luca` cwd. Before starting, inspect `herdr pane process-info`/`pane get` until the shell owns the foreground at the intended cwd. Explicit Herdr worktree provenance survives this directory change, so an unused anchor shell tab is not needed. Then start interactive Pi using the explicit fresh-session launch defaults above and verify its startup settings and actual cwd. Preserve the cwd of existing sessions instead of replacing them to enforce the new layout. If legacy multi-repo checkouts have no common ticket directory and no known coordinator cwd, ask where a new coordinator should start rather than moving the checkouts.
7. If the user requested work to start there, submit `herdr agent prompt` with the actual goal, intent, every checkout/branch, instructions to read this skill and the touched repos' `AGENTS.md`, and the role of independent persistent ticket owner. A Pi at the common directory does not automatically load context files inside sibling repos. If they asked only to open/resume a session, leave Pi at its prompt. Don't invent a preliminary slice or blanket bans on committing, PRs, or delegation; the ticket owner works toward reviewable PR(s) when asked to ship, without requiring one for exploration. Use Herdr for live startup/prompting; inspect progress and wait only when explicitly requested. `pi_sessions` is for past-session recall, transcript review, or recovery when a session is not live in Herdr—not a required setup step. Report workspace/pane/session IDs, checkout paths, branches, actual provider/model/thinking, and whether Pi is waiting or working, then hand control back. Startup/submission is not task completion and does not grant a supervisor role.

Herdr groups by Git repository, not an explicit hub-parent ID. Its expanded sidebar groups all workspaces with the same recorded `repo_key` and chooses the first recorded non-linked workspace as the displayed parent; unrelated workspaces between them in the raw list do not prevent nesting. Using `--workspace <hub-id>` selects the source repo, but cannot bind parentage when multiple recorded parents represent it. A different anchor repo can cause Herdr to open/reuse its own primary repo workspace; it is not another Luca hub. Research-only workspaces have no Git grouping.

If placement looks wrong, check `herdr workspace list`/`worktree list` for the hub's non-linked provenance and matching linked-ticket `repo_key` values. The CLI listing is flat, and the compact sidebar is also flat; expand the sidebar/group before treating this as failed setup. A primary-checkout lookup is not itself proof of the displayed parent. With competing recorded parents or persistent UI mismatch, explain the limitation and investigate rather than moving checkouts, recreating sessions, closing old workspaces, or promising a strict parent tree. Preserve focus with `--no-focus` and use returned IDs.

## Reuse and recovery

| Observed state | Action |
|---|---|
| Ticket checkout(s), workspace, and live owner exist | Reuse them, including older layouts/paths; opening again does not resubmit work. Adding a repo gives the same owner another checkout, not another Pi. |
| Checkout exists, ticket workspace/agent is absent | Open only the missing workspace from the anchor; recover the known session before considering a fresh Pi. |
| Ticket setup is partial | Add only missing repo checkouts or the missing Pi. Reuse existing branches, environment files, and service panes rather than rerunning everything. |
| Branch exists, checkout is absent | Preserve its tip at an unused path; do not recreate/reset it. If checked out elsewhere, reuse that path. If it is the primary checkout and isolation is needed, ask rather than switching it or forcing a duplicate. |
| Target path is occupied by different work, or a matching workspace has a missing/prunable checkout | Stop and explain the conflict; do not overwrite, prune, repair, or silently replace it. For a genuinely new ticket, choose a distinct unused path. |
| Setup/start failed or timed out | Re-read worktrees, workspaces, panes, and agents before retrying; partial success or another caller may have supplied what is missing. |

For live-owner startup/reuse checks, use `herdr agent get` and pane process metadata: do not interrupt or re-prompt a `working` run merely for setup; report a `blocked` owner as needing input, inspecting its request only when asked to continue/help; inspect the foreground process for `unknown` rather than assuming it stopped. Read only relevant startup/error/identity output when needed to resolve setup, not ticket findings or changes for an unrequested review. An idle owner can receive explicitly requested follow-up work, not an automatic replay of the original task. Resolve ambiguous owners/hubs before starting another agent. `agent start` requires an available foreground shell, not a pane running a server, editor, or agent; if no shell pane is available, add only the needed Pi pane/tab.

For a stopped owner, obtain its exact session reference from Herdr metadata or historical recall/transcript review, confirm it is not live elsewhere, and resume in an available pane of the owning workspace: `herdr agent start <unique-name> --kind pi --pane <pane-id> -- --session <known-session-path>`. Keep its original launch cwd and verify the resumed identity; do not guess with `--continue`, fork it, or launch a second live copy. Ask if the session/cwd cannot be identified. Merely reopening adds no task prompt; an explicit request to continue can receive a follow-up based on prior progress. Never close workspaces or remove checkouts as part of setup.

## Local environment

Opening/resuming a workspace or doing read-only research does not imply provisioning databases, seeding data, or starting servers. Set up only what the requested work needs. The `luca-ticket` helper targets the convention paths above; do not run it against a legacy checkout elsewhere or create a duplicate checkout just to use it—follow the repo's setup instructions and verify disposable database targets instead.

For convention-path checkouts, when a running environment or database-writing checks are needed, run `luca-ticket setup <ticket> --repos backend,ims` (omit either repo if not needed; supported repos are backend and IMS). Backend setup uses machine-local `~/.config/luca/local.env` (`references/local.env.example` shows keys); it creates **empty** per-ticket MySQL databases and ignored `.env`, while IMS gets an ignored `.env.local`. It preserves user-owned env files rather than overwriting them. For an updated backend checkout run `luca-ticket init <ticket> backend` to migrate and seed its fictional school; rerunning it is safe. `luca-ticket status <ticket>` reports ports/database names without credentials. Run backend tests via `luca-ticket test <ticket> backend -- [artisan-test-flags]` so PHPUnit cannot default to the shared `luca_backend_test`. For dev servers use the `backend_port`/`ims_port` shown by status; e.g. `php artisan serve --host=127.0.0.1 --port=<backend_port>` and `npm run dev -- --host 127.0.0.1 --port <ims_port> --strictPort`. IMS's local API URL override requires the matching `configURL` change in IMS; confirm it is present in the checkout before claiming the UI points at its ticket backend.

## Ticket owner's work and finish

These responsibilities apply inside the independent ticket session, not as instructions for the hub to supervise or verify it by default.

- Install dependencies, develop, run relevant checks, push requested PRs, and fix failures without routine permission prompts. Backend tests/migrations must use the ticket's disposable local/test DB; frontend-only builds need no database check. Local-only env reuse is fine once its targets are understood; don't assume the primary checkout's `.env` is safe or print secrets.
- Status should say what's running, what's done, and what remains; a finished agent is not itself a verified PR. For shipping work, include PRs and the actual tests/CI result; for investigation, give findings; for exploration, retain progress without manufacturing a PR.
- Close or remove a ticket only when asked. At cleanup time check running agents and dirty checkouts; preserve unmerged or uncommitted work. Never force-remove someone else's worktree or treat closing a workspace as deleting its Git branches.
